# NurChat — честная документация: шифрование и связь

> Статус: 2026-09. Маленькое ядро: **глухой relay + E2E**. Никакого P2P-транспорта
> в ядре нет (удалён как нерабочий муляж, см. «Что было убрано»).
> Здесь написано только то, что доказывается кодом. Ограничения — честно.

## 1. Модель одной фразой

Один relay (FastAPI) обслуживает всех. Relay **глухой**: он маршрутизирует
конверты, но прочитать переписку не может. Идентичность = локальная пара
ключей на устройстве. Приватный ключ устройство не покидает.

## 2. E2E-ядро (лички): X3DH + Double Ratchet

Реализации (зеркала друг друга):

- `frontend/src/services/doubleRatchet.ts` — браузер, боевая
- `shared/double_ratchet.py` — Python, для серверных тестов
- `frontend/src/services/e2e.ts` — менеджер сессий поверх ратчета
- `server/routes/keys.py` — раздача/сдача pre-key бандлов (сервер ключей
  не имеет, только публикует открытые половины)

Криптопримитивы: `@noble/curves` + `@noble/ciphers` (аудит cure53, 09.2024).
X25519 для DH, Ed25519 для подписей, XSalsa20-Poly1305 для сообщений,
HKDF-SHA-256 для вывода ключей.

Доказанные свойства и параметры (`doubleRatchet.ts`):

| Что | Значение |
|---|---|
| X3DH | **3 DH, без one-time prekey** — осознанно: в протоколе нет OPK id, получатель не смог бы выбрать правильный секрет и первое сообщение не расшифровалось бы. Это стандартный Signal-fallback, чуть слабее forward secrecy первого сообщения |
| Double Ratchet | симметричная цепочка + DH-ратчет на каждое сообщение |
| `MAX_SKIP_GAP` / `MAX_SKIPPED` | 2000 / 1000 (защита от перебора пропусков) |
| `PROTOCOL_VERSION` | 3 |
| Ротация | каждые 100 сообщений |
| Подпись | **обязательна**: сообщение без `senderSigningKey`/подписи или с невалидной подписью отбрасывается (`decryptMessage` возвращает `null`) |
| Бандл | клиент проверяет длины (identity 32 байта, SPK 32, подпись 64) и Ed25519-подпись SPK; сервер тоже проверяет подпись SPK при загрузке (`_verify_spk_signature`). Невалидный бандл = отказ, а не «продолжить без шифрования» |
| Safety Numbers | SHA-256 от отсортированной пары identity-ключей → 12 групп по 3 цифры (`e2e.ts: generateSafetyNumber`), сверка голосом/лично |

PreKey-цикл (`server/routes/keys.py`, `e2e.ts: setupPreKeys`):

1. Регистрация → генерация identity (X25519) + signing (Ed25519) пар.
2. Клиент генерирует SPK, подписывает, загружает (`POST /api/keys/signed-prekey`).
3. Клиент держит ~100 OPK, догружает когда остаток < 20.
4. Инициатор забирает бандл (`GET /api/keys/bundle/{user_id}`); сервер
   атомарно помечает OPK использованным. Клиент OPK из бандла
   **намеренно игнорирует** (см. X3DH выше) — это трата одного OPK,
   а не баг безопасности.
5. `POST /api/keys/cleanup` удаляет использованные OPK.

## 3. Групповые чаты: обёрнутый симметричный ключ + цепочка

`frontend/src/services/groupE2E.ts`, сервер хранит только завёрнутые копии
(`server/routes/chat.py`: `POST/GET .../group-key`, поле `Chat.group_key` —
JSON `{user_id: sealed}`).

- Ключ группы — случайные 32 байта (`generateGroupKey`).
- Каждому участнику ключ заворачивается через X25519 ECDH + secretbox
  (`wrapKeyForUser`) — сервер разворачивание выполнить не может.
- Каждое сообщение — уникальный ключ из хэш-цепочки (ratchet):
  компрометация текущего звена светит только будущее, не прошлое.
- Маршрутизация отправки (`useChatActions.ts`): **групповой чат всегда идёт
  через групповой ключ**, личка — через 1-1 Double Ratchet. Раньше был баг:
  группа, где у всех есть `public_key`, уходила в 1-1 сессию с первым пиром
  и остальные не могли расшифровать. Исправлено 2026-09.
- Live-расшифровка групп по WS (`ChatPage.tsx`) + расшифровка истории
  (`useChatMessages.ts`) — обе ветки (`group_encrypted` и 1-1) покрыты.

## 4. Хранение ключей на устройстве

`frontend/src/services/secureStorage.ts` (IndexedDB `nurchat-secure`):

- Приватные ключи лежат в IndexedDB, зашифрованные AES-256-GCM; ключ шифрования
  выводится из `device_secret` через PBKDF2 (100 000 итераций), сам ключ
  в WebCrypto помечен non-extractable.
- `device_secret` стабилен между логинами (токен меняется при каждом логине —
  шифровать им сессии нельзя, иначе расшифровка сломается после перелогина).
- Автоочистка кэша сессий после 10 минут неактивности; zeroize приватного
  материала после использования.

**Честное ограничение (не скрываем):** в браузере нет OS-keystore, поэтому
`device_secret` лежит в той же IndexedDB открытым текстом. Это выше планка,
чем localStorage (изолировано по origin, не утащить простым XSS-чтением
localStorage), но полный дамп IndexedDB её пробивает. Не заявляем
«военного уровня» там, где его нет.

## 5. Глухой relay: что он проверяет и что видит

Принуждение (`server/routes/chat.py: send_message`, `server/ws/chat_manager.py`):

- `RELAY_DEAF=true` (по умолчанию): **принимаются только сообщения с
  `encrypted_content`**. Plaintext отклоняется и по REST (400), и по WS
  (молча отбрасывается + warn в лог).
- `content` в БД при E2E всегда `"[encrypted]"`, рядом лежат непрозрачный
  конверт (`encrypted_content`) и подпись.
- После доставки всем (1-1: `delivered_at`, общее: фоновая чистка
  `MESSAGE_RETENTION_HOURS=48`) строки сообщений удаляются — история живёт
  только на устройствах.

Что relay **видит** (и это нормально для релея, но знай):

- членство в чатах, отправитель/получатели, время, размеры конвертов;
- read receipts, typing-индикаторы, mention-превью (**осторожно**: mention
  несёт `content_preview` до 100 символов исходного текста до шифрования —
  для E2E-чатов превью строится из `"[encrypted]"`, утечки текста нет);
- содержимое уведомлений = `"[encrypted]"`, т.к. `content` подменяется
  до рассылки нотификаций;
- **файлы НЕ E2E по байтам**: загрузки в `media/` хранятся открыто
  (случайные имена `file_*`, EXIF/GPS с фото счищается, TTL 30 дней +
  orphan-cleanup). Но **подпись вложения (caption) — E2E**: имя файла /
  «Голосовое сообщение» шифруется тем же маршрутом, что и текст
  (`handleSendAttachment`), иначе глухой relay отвечал 400 и файлы/войсы
  вообще не отправлялись. Настоящее file-E2E (байты) — следующий шаг,
  требует протокола прямой передачи (кандидат: WebRTC-datachannel
  между онлайн-устройствами);
- Защита аплоада: MIME по magic-bytes + жёсткий блок активного контента
  (svg/html/js), лимит 30/мин, ClamAV — оппортунистический (если стоит):
  вирус = 422, а **ошибка/таймаут сканера больше не блочит всех** (раньше
  битый ClamAV ронял вообще все загрузки), пропуск с warning в лог;
- IP: в БД не пишутся (`LOG_IPS=false`), но живут в памяти для rate-limit
  (WS: 10 соединений/IP) — иначе нельзя.

## 6. Транспорт между пользователями

| Канал | Эндпоинт | Как |
|---|---|---|
| REST API | `/api/...` | JWT Bearer + CSRF (`X-CSRF-Token`), таймаут клиента 15с, ретраи отправки 3× с backoff |
| Сообщения realtime | `/ws/chat/{user_id}?token=` | JWT из query (заголовки в WS невозможны), проверка `sub == user_id`, перепроверка токена каждые 10с, ping/probe при простое 120с, разрыв после 300с тишины, лимит 1 МБ/сообщение. Реконнект клиента: экспоненциальный backoff до 30с, макс 10 попыток, докачка пропущенного по HTTP |
| Звонки (сигналинг) | `/ws/calls/{user_id}`, `/ws/signaling/{user_id}` (синонимы) | offer/answer/ice-candidate + call-request/accept/reject/end/timeout, pending-буфер 50/пользователь с TTL 24ч, история в `CallLog` |
| Звонки (медиа) | WebRTC напрямую между устройствами | **Настоящий P2P**, сервер медиа не касается. ICE через `/api/calls/ice-servers` |
| Уведомления | `/ws/notifications/{user_id}` + Web Push (VAPID) | in-memory история (100/пользователь, теряется при рестарте); оффлайн — Web Push, мёртвые подписки (404/410) чистятся |
| Файлы | `/api/files/...?token=` | токен в query — иначе `<img>/<video>` не скачать (заголовки не послать) |

Токен в query — вынужденная мера (WS/медиатеги), mitigations: только `wss/https`
в проде, короткий TTL JWT, токен нигде не логируется сервером, а **uvicorn
access-лог выключен везде** (`--no-access-log` во всех лаунчерах и Dockerfile:
systemd-unit был уже, `start.bat`/`dev.bat`/`relay-home.bat`/`run.py` — починили
2026-09). Иначе JWT из `?token=` оседали бы в access-логах. Имена файлов
пользователей из логов тоже вычищены (только `file_id`).

NAT и звонки (честно): по умолчанию только публичные Google STUN.
**Без TURN звонки за NAT (мобильные сети, офисы) не соединятся.**
Прод требует coturn: `infra/coturn.conf` + `TURN_USERNAME`/`TURN_CREDENTIAL`
в `.env`. Сервер громко предупреждает в лог, если TURN не настроен.

CSP строится из CORS-whitelist (`CORS_ORIGINS`), а не из захардкоженного
localhost — иначе браузер режет удалённый relay. Ретранслятор за прокси:
`infra/nginx.conf` / `docker-compose.prod.yml` (Caddy), WS-апгрейд и таймауты
до 24ч уже прописаны.

## 7. Что было убрано (P2P) и что осталось

Убрано 2026-09 как мёртвый код (доказано grep: ничего не читало/не вызывало):

- `USE_P2P`, `P2P_*`, `USE_IPFS`/`IPFS_API_URL`, `USE_FEDERATED_BACKUP*` из
  `shared/config.py`;
- `src-tauri/src/p2p.rs` (TCP-«нода» на 127.0.0.1, ни одна команда не вызывала);
- P2P-экран/строки (`nurchat://`, LAN discovery, «Отправить через P2P»,
  «Очистить кэш P2P») из фронтенда; кнопка кэша теперь честно чистит только
  маркер оффлайн-синхронизации.

Остатки (не трогаем, но знаем):

- `p2pchat/` — старый прототип, ниоткуда не импортируется, исключён из линтов;
- таблицы `p2p_messages`/`p2p_backups` в `alembic/versions/001_initial_schema.py` —
  историческая миграция, новых не создаём;
- `src-tauri/src/ipfs.rs` — мёртвый импорт, кандидат на следующее удаление.

Почему не жалко (коротко): тот P2P не переживал NAT, требовал онлайна обоих
сторон и дублировал криптографический «салат». Приватность даёт E2E+глухой
relay, а P2P-медиа (звонки) никуда не девался. Возвращать P2P стоит только
точечно и рабочим: прямая передача файлов по WebRTC-datachannel.

## 8. Прод-чеклист оператора релея

1. Стабильные `ENCRYPTION_KEY`, `JWT_SECRET_KEY`, `TOTP_MASTER_KEY` в `.env`
   (автогенерация = потеря данных/сессий при рестарте).
2. `CORS_ORIGINS` = публичный домен релея; `VITE_API_HOST`/`VITE_API_PROTOCOL`
   у клиентов; `PUBLIC_RELAYS` в `frontend/src/config.ts` пуст — впишите свой
   relay, иначе клиенты default'ят на `127.0.0.1:8000`.
3. TURN (coturn) + `WEBRTC_ICE_SERVERS` или `TURN_*`, иначе звонки за NAT мертвы.
4. `RELAY_DEAF=true`, бэкап `.env` отдельно от БД, `LOG_IPS=false` по умолчанию.
5. Помнить: relay — центральная точка по метаданным и доступности.
   Следующий уровень — несколько независимых релеев + федерация
   (`USE_FEDERATION`, whitelist `FEDERATION_ALLOWED_SERVERS`).
